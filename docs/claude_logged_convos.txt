 4.  I'll add one more thing thats been on the docket here:  the :> syntax sugar has been an
  interesting conceptual extension.  We've tried to keep everything extremely simple and ultimately always map back
  down to =>, operating as if in a global state where all variables are always available, but it seems likely we'll
  want to have encapsulation/containment as a first class operation too.  Right now I'm thinking we will very likely
  want to do it like:   anything "contained within" another token is named in the global state as if its prefixed by
  that token (similar to folder/file path).  A :> B C  then is still just assigning AB and AC  (might be best as A.B
  A.C, using the . as operator syntax if we need to formalize.  We should make sure that works seamlessly conceptually
  with how we do decimal numbers too though).   We probably also want to use things like A B => A A(B) as a syntax to
  denote encapsulation (B enters into A when both present) and A A(B) => A B for extraction (if A contains B, take B
  out).  Those would affect state same as any rewrite rule, except B is reduced and AB (compiled form of A(B)) is
  increased (and vice-versa).  Basically, containerization just becomes syntactic sugar for writing general rules, but
  still compiles down into just tokens with prefixes.   Rules can still operate on tokens contained within other
  tokens (if they're exposed.  we'll probably have a concept of hiding information too, such that it is obscure and
  cant be operated on once inside another sign.  thats basically rule-creation logic though) or on the container token
  itself (though rules operating on the container itself must be ambiguous on the contents, even if empty, or else
  have the contents as part of the LHS preconditions e.g. A(B) = an A containing B.  Note though things get tricky
  when we're trying to represent this all with different container signs...  what if one A contains B, and another A
  contains C?  A A(B) A(C) => X  would trigger even if the same A didnt have both B and C, if those different As each
  had one.  This gets complex.  Moreover, it gets extra complex when it comes to actually representing state - because
  now we have object explosions.  Rule of thumb for now might be to treat all tokens of the same type as
  indistinguishable and part of the same thing (so there is no such thing as two different As.  if A contains B and A
  contains C, then A simply contains both.  no objects.  Any object is a new named variable with a unique prefix.
  these are merely containment classes, utilizing syntactic sugar ).   Anyway - like I said - a bit of a can of worms
  but it's still mostly coherent.  Hopefully not needed yet, as we seem to be able to model at least the Farm sims
  without this concept, but you can see in some of the other games that it really comes in handy.  It would also be
  nice to have rules that function only in particular spaces, which might be written like  A: B => C  (within A,
  convert B to C) which is just syntax sugar for AB => AC.  But then we start getting into the concept of state spaces
  within signs, for better or for worse.   And if we start thinking along those lines... well, a lot of stuff starts
  to look like just another state space.  All our probability universes we're running when we encounter a
  probabilistic rule - those could each just be the same set of rules, but with different prefixes.  It might even
  make sense to compute that way... rather than abstracting in compiler code which universe emulates when, we're just
  always running all of them we can fit into gpu, all operating on the same basic eternal X => Y syntax and the same
  like 5ish gpu cycles in perpetuity.  So yeah, some interesting pathways available there, but maybe for future
  expansion still.  Just wanted that on the record here, as it were, while we expand capabilities here.

  5.  One last major extension to the syntax being considered:  making A and A1 (A without a quantity and A1 with quantity 1) distinct.  Currently A <=> A1 as we just assume a 1 quantity, but we might want to make it that any rule which doesn't specify quantities is instead an *implies* rule which operates on boolean logic rather than quantity math, and crucially does *not* spend the LHS flags (does not turn them off to 0) when it turns on the RHS flags.  This would bridge two uses of signamancy rules we keep running into which are both similar but have different behaviors - as it's really easy to naively say `A => B` and expect it to mean "A implies B" but it actually currently means "A consumes 1 and produces 1 B" which is not what we want in all cases.  We want to be able to express those naive relationships AND to express quantity/consumption relationships in a single simple rule syntax, so I'm thinking that's likely making A and A1 distinct.  This piggybacks off the containerization stuff too - quantities are likely something we should see as a contained property of the parent sign, but the parent is a boolean existence sign.  Any sign has the same behavior - first it exists in a boolean sense, and then only if needed (by particular rules) does it have quantity logic too.  But then we get into stuff like 'whats the default quantity?' and all the usual runaway rule exploitation possibilities by having boolean rules basically able to create new containers with those defaults without cost which could lead to unchecked growth if not carefully setup in rules.  So it's a tradeoff, but a likely syntax path because "implies" rules are just too useful, and they're much cheaper to do computation with when applicable, so it incentivizes rules as boolean implies first.
